# inspirum-terminal SSH Acceptance Test Matrix

Status: Active acceptance record. Rows carry their own verification state; evidence is never extrapolated across platforms. This matrix is not a WindTerm parity claim.

## Issue #2 close gate

Issue #2 is narrower than the full long-term matrix below. Its close gate requires the integrated authentication/configuration/host-trust paths to be implemented, negative cases and cancellation/timeouts/disconnects to be exercised on disposable servers, native Windows/macOS/Linux smoke evidence to traverse the real Inspirum -> system OpenSSH path, unsupported methods to be explicit, and the same change to update this document.

`scripts/test-native-ssh-smoke.py` provides the cross-platform native gate. It starts a disposable loopback SSH server with throwaway Ed25519 host/client keys and isolated `known_hosts` files, then runs `tests/native_ssh_smoke.rs` through Inspirum's production `terminal::connect` path. The native test verifies configured-key authentication through an OpenSSH alias, terminal output/input, PTY resize, explicit reconnect, changed-host-key rejection before user authentication, and server-observed session/connection cleanup. No production host, user credential, or SSH configuration is used.

The deeper Linux fixture remains the method-specific gate for interactive password, encrypted-key prompt handling, SSH-agent, public-key + keyboard-interactive MFA, disabled authentication methods, prompt cancellation, stalled-handshake timeout, ProxyJump, forwarding, SFTP/SCP, tmux and process cleanup.

GSSAPI/Kerberos is **not claimed as an application-validated authentication method**. Inspirum exposes explicit `GSSAPIAuthentication` and `GSSAPIDelegateCredentials` policy switches to the installed system OpenSSH client, with delegation unset/off unless the user explicitly enables it, but CI has no disposable Kerberos realm. The product documentation therefore treats GSSAPI as a platform/OpenSSH-dependent pass-through capability rather than silently declaring it supported.

## Scope and status rules

- Targets: Windows x64, Linux x64, macOS Apple Silicon.
- Priority: SSH-first first slice; eventual WindTerm parity is not an acceptance claim.
- `System OpenSSH capability` describes the OS/client/server or external helper baseline only. It must never be treated as evidence of application support.
- `Application support` must be recorded independently as `Supported`, `Unsupported`, or `Platform-dependent`. Until verified, use `Pending (state unconfirmed)`; do not infer support from OpenSSH behavior.
- Every test starts with verification status `Pending`. Preserve confirmed unsupported and platform-dependent outcomes rather than converting them to failures or silently skipping them.
- Secrets must be synthetic and redacted from screenshots, logs, command lines, crash reports, and artifacts.

## Required evidence for every executed row

Record: test ID; application commit/build ID; clean/dirty tree state; OS/architecture/version; app configuration; system OpenSSH version and relevant capabilities; SSH server implementation/version/config; proxy/bastion versions where applicable; sanitized reproduction steps; timestamp; expected and observed behavior; application-support state; verification result (`Pass`, `Fail`, `Blocked`, or `Not applicable`); terminal/session logs with secrets redacted; screenshot or recording when UI behavior matters; server-side log excerpt; process/socket inventory before, during, and after; artifact hashes for transferred files; defect link for failures.

A `Pass` requires application-path evidence, not merely a successful `ssh`, `scp`, or `sftp` system-client control run. For platform-dependent or unsupported behavior, include the authoritative dependency/platform reason and the application's explicit, non-destructive user-facing response.

## Execution gates

1. Use isolated hosts, throwaway credentials, deterministic fixtures, and synchronized clocks.
2. Run positive and negative paths on every platform marked applicable; do not extrapolate across operating systems.
3. Establish the system OpenSSH control separately and label it `Baseline pass/fail/blocked`; a failed baseline may block application verification but cannot determine application support.
4. Record application support before assigning the test result. `Unsupported` or `Platform-dependent` is acceptable only when explicit and evidenced; it is not a pass unless the product requirement permits that state.
5. Treat credential disclosure, host-key bypass, trust-store corruption, proxy bypass, path traversal, unintended command execution, or orphaned security-sensitive resources as release-blocking failures.
